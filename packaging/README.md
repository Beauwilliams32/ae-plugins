# packaging/ — rebuilding the fleet against the Adobe AE SDK

The recovered source in `src/` is the *logic*. To turn it back into a loadable
`.plugin` you need Adobe's SDK, which is **not vendored here** (it is
Adobe-licensed; every plugin developer downloads it themselves and it must never
be committed).

## What this directory is for

It holds the parts of a build that are *ours* and that we can therefore verify:

| File | What it is |
|---|---|
| `<Plugin>PiPL.r` (16 files) | The PiPL resource for each effect, generated from `specs/<Plugin>.json` |

Regenerate them all with `node tools/render-pipl.mjs` (or `npm run recover`, which
runs the whole extract-and-render chain). The `.r` files are generated — edit the
spec or `tools/render-pipl.mjs`, never the output.

Everything else a bundle needs (`*.cpp`, `Info.plist`, code signature) is either
already recovered under `src/` or generated by the build.

## Getting the SDK

Download the After Effects SDK from Adobe and unpack it somewhere outside any
repo, then point `AE_SDK_DIR` at its `Examples` directory:

```bash
export AE_SDK_DIR="$HOME/.ae-sdk/<version>/<unpacked>/Examples"
```

`test/pipl.test.mjs` also auto-discovers an unpacked SDK under `~/.ae-sdk/`
(two levels deep) so a typical hand-unpacked install needs no configuration.
The SDK is distributed as a `.zip` wrapping a `.tar.zstd`, with Adobe's own
`zstd` binary and `extractzstd.sh` alongside it:

```bash
unzip -q AfterEffectsSDK_<ver>_mac.zip -d /tmp/sdk
cd /tmp/sdk/AfterEffectsSDK_<ver>_mac
./extractzstd.sh                      # uses the bundled zstd
```

## Version pinning — verified, not assumed

All 16 shipped bundles report spec version `0x000d001d` in their `eSVR` PiPL
atom. That encodes `PF_PLUG_IN_VERSION 13` and `PF_PLUG_IN_SUBVERS 29`, which is
exactly what **AE SDK 25.6** declares in `Examples/Headers/AE_EffectVers.h`. So
SDK 25.6 is the drop this fleet was built from, and a rebuild against it will
claim the same spec version as the shipped plugins. `test/pipl.test.mjs` asserts
this rather than trusting it, and fails loudly if the local SDK disagrees.

The compiler side is also verified: the SDK's own
`Examples/Template/Skeleton` sample compiles clean for `arm64` with

```bash
clang++ -std=c++17 -O2 -c -arch arm64 \
    -I "$AE_SDK_DIR/Headers" -I "$AE_SDK_DIR/Headers/SP" -I "$AE_SDK_DIR/Util" \
    Skeleton.cpp
```

Note the `-I "$AE_SDK_DIR/Headers/SP"` — `AE_GeneralPlug.h` includes `SPBasic.h`,
which lives in the `SP` subdirectory, and omitting that flag is the first thing
that fails on a fresh setup.

## The byte-identity proof

The strongest evidence that a recovered spec is *complete* is to rebuild the
shipped artifact from it and get the same bytes back. PiPLs are ideal for this:
they are pure data, so there is no compiler freedom to excuse a difference.

`test/pipl.test.mjs` does exactly that for **all 16 effects**:

```bash
npm test -- --test-name-pattern="byte-identical"
```

It rezzes each `packaging/<Plugin>PiPL.r` and compares against the PiPL inside the
installed `<Plugin>.plugin`. Current result: **all 16 are byte-identical across the
entire 576-byte payload — the 16-byte resource-file header plus the 320-byte PiPL
resource.**

The test is verified not to be vacuous: flipping a single bit in one global
out-flags word makes it fail with `NoiseField: the PiPL payload differs from the
shipped bundle`. A pair of identical-but-empty resources cannot pass, because the
test also asserts each atom (kind, name, category, entry points, both version
words, both flag words, match name) is present in the rebuilt bytes.

One byte outside that region does differ: the resource map's `fileRefNum` field
is `0x000a` when Rez writes the file and `0x0009` in the shipped bundle. That
field is the resource file's own reference number, recorded by whatever tool
produced the file; it is not PiPL content, it is not read when the plugin loads,
and it is not something a source file can influence. Everything the PiPL actually
asserts — kind, name, category, `mi64`/`ma64` entry points, PiPL version, spec
version, effect version, info flags, both global out-flag words, match name, and
the trailing `aeFL` reserved word — matches exactly.

To inspect a shipped PiPL by hand, note that the resource file is a **data fork**
resource file, so `DeRez` needs `-useDF` or it fails with `eofErr (-39)`:

```bash
DeRez -useDF -only PiPL \
  "/Applications/Adobe After Effects 2026/Plug-ins/Williams Media/SpectraKeys.plugin/Contents/Resources/SpectraKeys.rsrc"
```

## Known naming inconsistency

15 of the 16 effects use a `WM_<Name>` match name. **SpectraKeys alone is
`WMH SpectraKeys`** — the only outlier in the fleet, and almost certainly the
first effect built, before the convention settled. `specs/SpectraKeys.json`
records it as `WMH SpectraKeys` because that is what the shipped bundle contains,
and the byte-identity proof would fail if it recorded anything else.

Renaming it to `WM_SpectraKeys` is a deliberate behaviour change, not a recovery:
AE identifies effects by match name, so it would break any project that already
uses the current name. It is therefore left as found.

## What is NOT done yet

Being explicit so this directory is not mistaken for more than it is:

- There is **no `EffectMain`** for any effect. The recovered `src/` code is the
  DSP and parsing core; the AE entry point, parameter registration and render
  callbacks have not been rewritten. Until they exist, nothing here produces a
  loadable `.plugin`.
- No `Info.plist`, no bundle assembly, no code signing.

The remaining gap is therefore `EffectMain` and the render pipeline, not the
plugin metadata: the metadata round-trips exactly.
